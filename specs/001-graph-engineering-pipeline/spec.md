# Feature Specification: 曖昧な依頼から動くものまでを通し切る工程

**Feature Branch**: `001-graph-engineering-pipeline`

**Created**: 2026-08-28

**Status**: Draft

**Input**: User description: "添付レポートで整理した Graph Engineering の仕組みを構築する。曖昧な依頼を受け取ってから、動くものが返るまでを、既存手法（Opportunity Solution Tree / Shape Up / Lean Startup の Critical Assumption / NASA の原則 / Logical Decomposition / Graph 実行）の組み合わせで通し切れる状態にする。"

## Problem *(mandatory)*

工程の部品は揃っているのに、**依頼を1本も通していません。** 原則・雛形・判定表・検査スクリプトは設置済みで、部品単位では動作を確認しています。しかし「依頼を渡す」から「動くものが返る」までを端から端まで走らせた事実がありません。したがって、どこで詰まるのか、何が足りないのかが分かっていません。

部品が揃っているのに通していない状態が続くと、整備した時間が納品物に化けないまま増えます。

### Desired Outcome

依頼を1文で渡したあと、依頼者が途中を見に行かなくても、依頼どおりに動くものが返ってくること。1件の依頼について依頼者が応答を求められる回数が0に近いこと。

### Opportunities

- 工程を端から端まで走らせた事実が無く、どこで詰まるかが分かっていない
- 「できました」と報告されたものが実際に動くかどうかを、依頼者が自分で確かめる手段が無い
- 途中で失敗したとき、どこまで戻ればよいかが決まっておらず、全部やり直しになりやすい
- 部品の整備だけが進み、動くものが1つも増えない状態に陥りやすい

## Appetite *(mandatory)*

**2週間。** ただし時間より強い制約を1つ置きます。**この工程に新しく足してよいのは、実際に1本通す過程で詰まった箇所だけです。** 先回りして仕組みを作り込む時間は0とします。2週間で通し切れない場合は、期間を延ばさずに扱う依頼を小さくします。

## Solution *(mandatory)*

設置済みの6段の工程に、**実際の依頼を1本流します。** 流す過程で詰まった箇所だけを直し、通し切った事実と数値を記録します。新しい仕組みを先に作りません。

流す対象は、この工程自体ではなく**別の小さな依頼1本**とします（工程で工程を作ると、詰まりの原因が工程の側か対象の側か切り分けられなくなるため）。

## Rabbit Holes

- 実装フェーズを実際に動かすと、依頼者への確認が想定外の箇所で発生する可能性がある（着手判定で止まったときの続行可否は既知の1回。それ以外が出るかは未確認）
- 失敗した箇所だけを再実行する方式が、実際の失敗で使い物になるかは未検証
- 受入検査の雛形はブラウザ操作を前提としており、画面を持たない依頼では別の形の証拠が要る
- 並列実行のトークン消費が、逐次実行に対してどれだけ増えるかを測っていない

## No Gos *(mandatory)*

- 新しい概念・名称・指標の考案（Goal Contract、独自 Risk 分類、独自スコア、追加のゲート）
- 実行基盤の自作（Orchestrator、状態機械、再実行機構）
- 100件の並列運用の実現。今回は1本を通し切ることだけを扱う
- 依頼者向けの画面・ダッシュボードの作成

## 2. User Scenarios & Testing — 検収条件 *(mandatory)*

### User Story 1 - 依頼を1文渡すと、動くものが返る (Priority: P1)

依頼者が1文渡し、そのあと二択に1回答えるだけで、動くものと、それが動いた証拠が返る状態にします。

**Why this priority**: これが通らなければ、この工程は存在しないのと同じです。

**Independent Test**: 小さな依頼を1本渡し、返ってきたものが実際に動くかを確認するだけで検証できます。

**Acceptance Scenarios**:

1. **Given** 工程が設置済みで、依頼者が作りたいものを1文だけ持っている。**When** その1文を渡し、返ってきた二択に1回答える。**Then** 仕様・計画・作業一覧・実装が生成され、機械検査がすべて緑になり、依頼者が応答を求められた回数が**その二択1回だけ**である。
2. **Given** 依頼を1本通し終えている。**When** 依頼者が納品物を受け取る。**Then** 「壊れていた証拠 / 直った証拠 / 戻すと同じ壊れ方に戻る証拠」の3点が揃った状態で示される。

---

### User Story 2 - 準備ができていない依頼は、実装に入る前に止まる (Priority: P1)

前提が確かめられていないまま実装が進み、あとで作り直しになることを防ぎます。

**Why this priority**: 止まらなければ、曖昧なまま分解する以前の状態に戻ります。

**Independent Test**: 着手判定に未チェックを残したまま実装を起動するだけで検証できます。

**Acceptance Scenarios**:

1. **Given** 着手判定に未チェックの項目が1つ以上残っている。**When** 実装を起動する。**Then** 着手前に停止し、実装対象のファイルが1つも変更されていない。

---

### User Story 3 - 失敗したところだけをやり直せる (Priority: P2)

1か所の失敗で全部が作り直しになることを防ぎます。

**Why this priority**: これが無いと、規模が大きくなるほど失敗の代償が増えます。

**Independent Test**: 複数に分けた作業のうち1つだけを意図的に失敗させ、その1つだけを直して緑にできるかで検証できます。

**Acceptance Scenarios**:

1. **Given** 作業を複数に分けて実行し、そのうち1つだけが検査で落ちている。**When** 落ちた1つだけを直して再実行する。**Then** 成功していた他の作業を作り直さずに、全体が緑になる。

---

### Edge Cases

- 依頼が Solution（作りたいものの形）として語られた場合に、上位の目的まで遡れずに詰まらないこと
- 通す過程で前提が崩れた場合に、実装の修正ではなく前提の見直しへ戻れること
- 画面を持たない依頼で、動いた証拠を何で示すかが決まっていること

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 工程は、依頼文1文を入力として受け取り、仕様・計画・作業一覧・実装・検査結果を出力する
- **FR-002**: 依頼者への確認は、ゴールを決めるときの二択1回に限る
- **FR-003**: 着手判定に未チェックが残っている間は、実装に着手しない
- **FR-004**: 完了の主張には、機械が実行した検査の出力を添える
- **FR-005**: 失敗した作業単位を特定でき、その単位だけを再実行できる
- **FR-006**: 1本通した結果として、所要時間・トークン消費・依頼者の応答回数・再実行回数を記録する

### Key Entities *(データを扱う場合のみ)*

- **依頼**: 依頼者が渡す1文
- **仕様**: 目的・阻害要因・介入・上限・やらないこと・前提・検収条件
- **作業単位**: 依存関係と並列可否を持つ、成果物1つ分の作業
- **証拠**: 機械が出した検査の出力

## 4. 停止4領域 (Fail Fast) *(mandatory)*

- **金額**: なし（この工程では金額を扱いません）
- **日付**: なし（記録に日付を書く以外に日付の計算を行いません）
- **権限**: なし（この工程自体は画面や認証を持ちません。ただし成果物を外部へ公開する操作は、依頼者の指示があるときだけ行います）
- **データの削除・上書き**: あり。検査スクリプトの書き換え、仕様の上書き、作業結果の統合。**検査を弱める変更と、確認していない上書きは、その場で停止します**

### 保護対象ルート一覧

- NONE

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 依頼1本あたり、依頼者が応答を求められる回数が **1回**（ゴールを決めるときの二択）である
- **SC-002**: 依頼を渡してから動くものが返るまでに、依頼者が途中経過を見に行った回数が **0回** である
- **SC-003**: 完了報告の **100%** に、機械が実行した検査の出力が添えられている
- **SC-004**: 1か所の失敗に対して作り直す作業単位が、**その1単位だけ**である（全体の作り直しが発生しない）
- **SC-005**: 1本通した結果の記録（所要時間・トークン消費・応答回数・再実行回数）が **1件** 残っている

## Assumptions *(mandatory)*

### Critical Assumptions (Assumption Tests)

| # | Assumption | 偽だったら何が変わるか | Evidence | 状態 |
|---|---|---|---|---|
| CA-001 | 1本通せば、足りない接続部分が具体的に分かる | Solution の変更。通すだけでは不足が見えないなら、別の見つけ方が要る | | 未確認 |
| CA-002 | 依頼者への確認を、ゴールを決めるときの二択1回に保てる | Opportunity の見直し。確認が増えるなら、依頼者の手間は減っていない | | 未確認 |
| CA-003 | 失敗した作業単位だけを再実行する方式が、実際の失敗で使い物になる | Solution の縮小。使えないなら、逐次実行に戻して規模を諦める | | 未確認 |
| CA-004 | 画面を持たない依頼でも、動いた証拠を機械の出力で示せる | Solution の変更。示せないなら、扱う依頼を画面のあるものに限る | | 未確認 |

### Non-critical Assumptions

- 通しに使う依頼は小さいものでよい（規模は今回の関心事ではない）
- 記録の置き場所は既存の記録ファイルでよい
- 使用する既存手法の組み合わせは決定済みで、今回変更しない
